스킬 하나를 설치해두면 평소에는 이름과 설명만, **약 100토큰**을 차지한다. 요청이 그 설명과 맞아떨어질 때 비로소 본문(5k 토큰 미만)이 로드되고, 딸려 있는 참고 파일과 스크립트는 실제로 읽거나 실행할 때까지 **비용이 0**이다. 스크립트는 bash로 돌아가기 때문에 코드 본문은 컨텍스트에 들어가지 않고 출력만 들어간다. (Anthropic 공식 문서 「Agent Skills」, 2026-08-06 확인)

이게 에이전트에 사내 지식을 싣는 방식이 프롬프트 붙여넣기에서 파일 적재로 넘어간 이유다. 스킬 20개를 깔아도 평시 비용은 2천 토큰 남짓이고, 그중 오늘 쓰는 하나만 펼쳐진다.

## 스킬: 필수 필드는 두 개뿐, 승부는 description에서 난다

`SKILL.md` 파일 하나가 전부다. YAML frontmatter에서 필수 필드는 `name`과 `description` 둘뿐이다. `name`은 최대 64자에 소문자·숫자·하이픈만 쓸 수 있고 "anthropic", "claude"는 예약어라 못 쓴다. `description`은 최대 1024자다. (Anthropic 공식 문서, 2026-08-06 확인)

문서가 명시적으로 요구하는 건 description의 내용이다. **무엇을 하는지와 언제 써야 하는지를 둘 다 담아야 한다.** 이 문장이 모델이 요청과 대조하는 유일한 트리거 기준이기 때문이다. "PDF 처리 도구"라고만 쓴 스킬은 설치돼 있어도 호출되지 않는다. "PDF에서 표와 텍스트를 추출하고 양식을 채운다. 사용자가 PDF·양식·문서 추출을 언급할 때 사용"처럼 발동 조건까지 써야 걸린다.

실무에서 자주 밟는 함정은 배포 쪽에 있다. 공식 문서는 **커스텀 스킬이 서피스 간에 동기화되지 않는다**고 못 박는다. claude.ai에 올린 스킬은 API에서 쓸 수 없고, API에 올린 것은 claude.ai에 없으며, Claude Code 스킬은 파일시스템 기반이라 양쪽 모두와 별개다. 공유 범위도 다르다 — claude.ai는 개인 단위(팀원이 각자 올려야 하고 관리자 일괄 배포가 없다), API는 워크스페이스 전체, Claude Code는 개인(`~/.claude/skills/`) 또는 프로젝트(`.claude/skills/`)다.

런타임 제약도 서피스마다 다르다. Claude API에서 도는 스킬은 **네트워크 접근이 없고 런타임에 패키지를 설치할 수 없다**. 사전 설치된 패키지만 쓸 수 있다. 반대로 Claude Code의 스킬은 사용자 컴퓨터의 다른 프로그램과 동일한 전체 네트워크 접근 권한을 갖는다. 같은 SKILL.md가 두 곳에서 다르게 동작한다는 뜻이라, 이식할 때 외부 호출부터 확인해야 한다. (이상 Anthropic 공식 문서, 2026-08-06 확인)

## Tasks: 몇 시간짜리 작업을 연결 유지 없이 다루기

MCP 스펙 **2026-07-28** 리비전은 베이스 프로토콜을 무상태(stateless)로 두고 요청 단위로 능력을 협상한다. 그리고 오래 걸리는 일은 별도 확장인 **Tasks**로 뺐다. (MCP 공식 스펙, 2026-07-28)

동작은 단순하다. 서버가 "이 요청은 오래 걸린다"고 판단하면 결과 대신 `taskId`가 담긴 핸들을 돌려주고, 클라이언트는 `tasks/get`으로 폴링한다. 상태는 다섯 가지다 — `working`, `input_required`, `completed`, `failed`, `cancelled`. 뒤의 셋은 터미널 상태라 한 번 도달하면 바뀌지 않는다. (MCP 공식 문서 「Tasks」, 2026-08-06 확인)

여기서 실무적으로 의미 있는 건 두 가지다.

**첫째, 승인 게이트가 프로토콜 안으로 들어왔다.** 작업 도중 사람의 확인이 필요하면 상태가 `input_required`로 바뀌고 `tasks/get` 응답에 `inputRequests`가 실린다. 클라이언트는 `tasks/update`로 답한다. 별도 커넥션도, 서버가 클라이언트에 먼저 말을 거는 채널도 필요 없다. 공식 문서는 Tasks의 적합 사례로 "승인 게이트, 리뷰 단계, 사용자 확인을 위해 멈추는 모든 작업"을 명시한다.

**둘째, `taskId`는 durable handle이다.** 클라이언트가 끊기거나 재시작해도 같은 ID로 폴링을 재개할 수 있다. 대신 클라이언트 쪽에 숙제가 생긴다 — 공식 구현 가이드는 크래시·재시작 이후를 위해 **task ID를 영속 저장하라**고 요구한다. 메모리에만 들고 있으면 이 확장을 쓰는 의미가 사라진다.

## 함께 읽어야 할 한계

**취소는 보장이 아니다.** 공식 문서는 `tasks/cancel`이 협조적(cooperative)이라고 명시한다. 서버는 취소 의도를 확인할 뿐 작업을 중단할 의무가 없고, 작업은 `cancelled`가 아닌 다른 터미널 상태에 도달할 수 있다. "정지 버튼을 눌렀으니 멈췄겠지"를 전제로 과금이나 외부 반영을 설계하면 안 된다.

**확장은 양쪽 opt-in이다.** MCP 확장은 항상 opt-in이고 클라이언트와 서버 양쪽의 명시적 지원 및 초기화 시 협상이 필요하다. 서버는 클라이언트가 확장을 선언하지 않았으면 절대 task를 반환해선 안 된다. 클라이언트별 지원 현황은 제각각이므로, 도입 전 쓰는 클라이언트가 Tasks를 지원하는지부터 확인해야 한다.

**스킬은 설치할 소프트웨어로 취급해야 한다.** Anthropic은 신뢰할 수 있는 출처의 스킬만 쓰라고 경고하면서, 악성 스킬이 데이터 유출이나 무단 시스템 접근으로 이어질 수 있다고 적는다. 특히 외부 URL에서 데이터를 가져오는 스킬은 그 외부 내용 자체가 악의적 지시를 담을 수 있어 위험하고, 신뢰할 만한 스킬도 외부 의존성이 나중에 바뀌면 오염될 수 있다. MCP 스펙 쪽도 같은 방향이다 — 도구 설명과 annotation은 신뢰된 서버에서 온 것이 아니면 신뢰할 수 없는 것으로 취급하고, 호스트는 도구 호출 전에 사용자의 명시적 동의를 받아야 한다. 한 가지 더, Agent Skills는 ZDR(zero data retention) 적용 대상이 아니다.

**성과 수치는 출처의 성격을 보고 읽어야 한다.** 인공지능신문이 2025년 12월 21일 소개한 구글 「2026 AI 에이전트 트렌드 보고서」에는 텔러스가 임직원 57,000명 이상에게 AI를 적용해 상호작용당 평균 40분을 줄였고, 수자노가 데이터 질의 시간을 95% 줄였으며, 댄포스가 거래성 의사결정의 80%를 자동화해 응답시간을 42시간에서 거의 실시간으로 당겼고, 맥쿼리 은행이 사기 탐지 오탐을 40% 줄였다는 사례가 실렸다. 방향은 참고할 만하지만 모두 벤더가 자사 고객 사례로 발표한 수치다. 자사 도입 근거로 쓰려면 같은 조건인지부터 따져야 한다.

## 한 줄 정리

지식은 스킬 파일로 실어 필요할 때만 펼치고, 오래 걸리는 일은 Tasks 핸들로 넘겨 승인과 재시작을 프로토콜에 맡긴다 — 단, 취소는 보장되지 않고 스킬은 설치할 소프트웨어라는 두 가지 전제 위에서다.
