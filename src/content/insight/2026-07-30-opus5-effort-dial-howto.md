## 새 모델로 옮기면서 추가할 게 아니라 지울 게 있다

Anthropic이 Claude Opus 5 마이그레이션 문서에 적어둔 지침 중 하나는 무언가를 넣으라는 게 아니라 빼라는 것이다.

> "시키지 않아도 스스로 자기 작업을 검증하므로, 이전 모델에서 가져온 검증 지시문("최종 검증 단계를 포함하라", "서브에이전트로 검증하라")을 제거하라. Claude Opus 5에서는 과잉 검증(over-verification)을 유발한다."
> — Anthropic, What's new in Claude Opus 5 (Claude Platform Docs, 2026년 7월 24일 릴리스 기준)

프롬프트에 한 줄 남겨둔 습관이 그대로 토큰 청구서가 되는 구조다. Opus 5는 2026년 7월 24일 출시됐고, 가격은 입력 100만 토큰당 5달러 / 출력 100만 토큰당 25달러로 Opus 4.8과 같다(Anthropic 공식 발표, 2026년 7월 24일). 가격표가 그대로인데 같은 프롬프트로 토큰을 더 쓰게 되는 경로가 몇 개 생겼다는 뜻이다. 아래는 벤더 공식 문서에서 확인한 것만 정리한 실무 조정 목록이다.

## 1. effort 다이얼은 올리는 게 아니라 내리는 쪽이 기본이다

Opus 5의 주 통제 수단은 `effort` 파라미터다. Anthropic은 릴리스 노트에서 "effort는 Claude Opus 5를 조종하는 주요 통제 수단"이라고 못 박았다(Claude Platform 릴리스 노트, 2026년 7월 24일). 5단계 래더는 다음과 같다(Anthropic Effort 문서 기준).

| 레벨 | 문서상 용도 |
|---|---|
| `low` | 서브에이전트처럼 속도·최저비용이 중요한 단순 작업 |
| `medium` | 속도·비용·성능의 균형이 필요한 에이전트 작업 |
| `high` | 복잡한 추론, 어려운 코딩 문제, 에이전트 작업 (**API 기본값**) |
| `xhigh` | 30분을 넘는 장시간 에이전트·코딩 작업, 토큰 예산이 수백만 규모일 때 |
| `max` | 가장 깊은 추론과 철저한 분석이 필요한 작업 |

여기서 세대 간 권장 시작점이 뒤바뀐 게 실무 포인트다. Opus 4.7과 4.8 문서는 "코딩·에이전트 용도는 `xhigh`로 시작하라"고 안내한다. Opus 5 문서는 다르다. "기본값인 `high`로 시작하고, 평가(evals)에 따라 조정하라"면서 품질이 유지되는 곳이라면 "`low`와 `medium`을 토큰 비용과 응답 시간의 주 통제 수단으로 **적극(liberally)** 사용하라"고 권한다(Anthropic Effort 문서).

같은 문서는 이전 모델에서 쓰던 effort 설정을 그대로 들고 오지 말라고도 적었다. "이전 모델에서 effort 설정을 가져왔다면, 재사용하지 말고 평가 세트에서 effort 스윕을 새로 돌리라"는 것이다. 4.8에서 `xhigh`로 굳혀둔 설정을 그대로 옮기면, 권장 시작점이 두 칸 낮아진 모델에 두 칸 높은 값을 물려두는 셈이 된다.

한 가지 오해는 미리 정리하는 게 좋다. effort는 토큰 예산이 아니다. 문서는 "effort는 행동 신호(behavioral signal)이며 엄격한 토큰 예산이 아니다"라고 명시한다. 낮은 레벨에서도 충분히 어려운 문제면 모델은 여전히 사고하고, 다만 높은 레벨보다 덜 사고한다.

## 2. effort는 텍스트만이 아니라 도구 호출 횟수를 바꾼다

effort가 프롬프트 엔지니어링의 다른 손잡이들과 다른 지점은 적용 범위다. Anthropic 문서는 effort가 **응답의 모든 토큰**에 영향을 준다고 설명한다. 텍스트 응답과 설명, 사고(활성 시), 그리고 **도구 호출과 함수 인자**까지다. 문서가 든 예시는 직접적이다. "낮은 effort는 Claude가 도구 호출을 더 적게 한다는 뜻이다."

문서가 정리한 낮은 effort의 행동 경향은 이렇다. 여러 작업을 더 적은 도구 호출로 통합하고, 호출 수 자체가 줄고, 서두 없이 곧바로 실행하고, 완료 후 간결한 확인 메시지를 남긴다. 높은 effort는 반대로 호출이 늘고, 실행 전에 계획을 설명하고, 변경사항을 상세히 요약한다.

에이전트 워크로드에서 비용의 상당 부분이 도구 호출 왕복에서 나온다면, effort 한 칸이 사고 길이보다 호출 횟수에서 먼저 체감될 수 있다는 뜻이다. 대신 착각하기 쉬운 방향이 하나 있다. Opus 5에서 effort는 **눈에 보이는 응답 길이를 줄이는 손잡이가 아니다**. 문서는 "effort는 사고량을 통제하지 가시적 응답 길이를 통제하지 않는다. Opus 5에서 effort를 바꿔도 응답이 안정적으로 짧아지지 않으므로, 길이는 프롬프트로 지시하라"고 적었다.

## 3. 사고 비활성화 + 높은 effort = 400 에러

Opus 4.8에서 4.8용 코드를 그대로 옮길 때 실제로 요청이 깨지는 지점이 하나 있다. Opus 5에서 사고(thinking) 비활성화는 effort가 `high` 이하일 때만 허용된다. `thinking: {"type": "disabled"}`를 `xhigh`나 `max`와 함께 보내면 **400 에러**가 반환된다. Anthropic은 이를 "Opus 4.8로부터의 파괴적 변경(breaking change)"이며 요청마다 강제되는 정식(GA) 동작이라고 명시했다(Claude Platform 릴리스 노트 및 What's new in Claude Opus 5, 2026년 7월 24일). Opus 4.8에서는 사고 비활성화가 effort 레벨과 무관했다.

해법은 문서가 두 갈래로 제시한다. 사고 비활성화를 유지하려면 effort를 `high` 이하로 내리고, effort를 유지하려면 `thinking` 필드를 제거하는 것이다.

다만 문서는 사고를 끄는 선택 자체를 권하지 않는다. 사고를 비활성화하면 Opus 5가 간헐적으로 `tool_use` 블록 대신 텍스트 출력에 도구 호출을 써버리거나, 가시 응답에 내부 XML 태그를 포함할 수 있다고 경고한다. 그래서 결론은 이렇게 적혀 있다. "가능하면 사고를 활성 상태로 두고, 토큰 비용은 더 낮은 effort 레벨로 통제하라."

여기에 딸려 오는 조정이 `max_tokens`다. Opus 5는 사고가 기본 활성이고, `max_tokens`는 사고와 응답 텍스트를 합친 총 출력의 하드 리밋이다. 문서는 Opus 4.8에서 사고 없이 돌던 워크로드는 이 값을 다시 볼 것을 권하고, `xhigh`나 `max`로 돌릴 때는 서브에이전트와 도구 호출을 감당할 여유를 두라며 "64k 토큰에서 시작해 조정하는 것이 합리적 기본값"이라고 안내한다.

## 4. 캐시를 지키려면 effort를 대화 중간에 바꾸지 말 것

비용 얘기가 나오면 프롬프트 캐싱이 따라오는데, effort와 캐싱은 서로 간섭한다. Anthropic 문서의 설명은 명확하다. "effort가 렌더링된 프롬프트의 형태를 바꾸기 때문에, 요청 사이에 effort를 변경하면 이전 턴의 캐시된 프리픽스가 보존되지 않는다. 긴 세션에서 프롬프트 캐싱에 의존한다면 시작할 때 effort 레벨을 정하고 그대로 유지하라."

같은 문서의 베스트 프랙티스는 이를 한 줄로 정리한다. effort는 **워크로드 사이에서** 바꾸고, 캐시 히트에 의존하는 **하나의 대화 안에서는** 바꾸지 말라는 것. 태스크 난이도에 따라 effort를 동적으로 조절하는 설계가 매력적으로 보이지만, 캐시를 함께 쓰는 세션 안에서는 그 유연성이 캐시 무효화 비용으로 돌아온다.

반대로 캐싱 쪽에서 조건이 완화된 것도 있다. Opus 5의 최소 캐시 가능 프롬프트 길이는 **512 토큰**으로, Opus 4.8의 1,024 토큰에서 내려갔다. 문서는 "Opus 4.8에서는 너무 짧아 캐시할 수 없던 프롬프트가 이제 **코드 변경 없이** 캐시 항목을 만들 수 있다"고 적었다. 짧은 시스템 프롬프트로 운영하던 워크로드는 아무것도 고치지 않고 캐시 적중 범위가 넓어진 경우다.

## 5. 도구 목록은 이제 세션 내내 고정하지 않아도 된다

에이전트를 오래 돌릴 때 흔한 낭비가 세션 내내 모든 도구를 물려두는 것이다. 도구 정의는 프롬프트의 캐시되는 앞부분에 들어가므로, 필요 없는 도구를 빼려면 캐시를 깨야 했다.

2026년 7월 24일부터 이 제약에 베타 우회로가 생겼다. **대화 중 도구 변경(mid-conversation tool changes)** 이다. 릴리스 노트 표현은 이렇다. "대화의 턴 사이에 도구를 추가하거나 제거하면서 프롬프트 캐시를 유지한다." What's new 문서는 "세션 내내 고정된 도구 목록을 재전송하는 대신"이라는 대비를 덧붙였다. 사용하려면 요청에 `mid-conversation-tool-changes-2026-07-01` 베타 헤더를 포함해야 하고, 지원 모델은 Claude Fable 5, Claude Mythos 5, Claude Opus 4.8, Claude Opus 5다.

같은 날짜에 함께 들어온 운영 편의 기능도 둘 있다. `fallbacks` 파라미터의 `"default"` 모드는 직접 관리하는 모델 목록 대신 Anthropic 권장 폴백 모델을 거부(refusal) 카테고리별로 적용한다(`server-side-fallback-2026-07-01` 헤더 필요, 전체 파라미터가 베타). 그리고 7월 22일부터 Claude Managed Agents는 에이전트의 모델 설정 안에 `effort`를 직접 지정할 수 있게 됐다(`model` 객체 안에 전달).

에이전트 프레임워크 쪽 그림도 같은 방향이다. OpenAI Agents SDK 공식 문서는 Agent(지시문 + 도구), 다른 에이전트에 특정 작업을 위임하는 핸드오프, 입출력을 검증하는 Guardrails, 에이전트 루프를 도는 Runner, 루프 안에서 작업 맥락을 유지하는 영속 메모리 계층 Sessions를 핵심 구성요소로 제시하고, "워크플로를 시각화·디버깅·모니터링하는 내장 트레이싱"과 "진정으로 격리된 워크스페이스에서의 실행"을 지원한다고 설명한다(OpenAI Agents SDK 공식 문서). 도구를 한 번에 다 물리지 않고 필요한 시점에 붙이는 것, 그리고 루프 밖에서 관측하는 것이 양쪽 벤더가 공통으로 밀고 있는 형태다.

## 균형: 다이얼 조정으로 해결되지 않는 것들

여기까지는 설정 이야기다. 설정이 해결하지 못하는 문제를 같이 봐야 한다.

첫째, 앞서 인용한 성능 근거는 대부분 벤더 자체 측정이다. Anthropic 발표문 기준으로 Opus 5는 Frontier-Bench v0.1에서 Opus 4.8 성능의 두 배를 넘겼고(태스크당 비용은 더 낮음), CursorBench 3.2에서 Fable 5 최고 점수와 0.5% 이내 차이를 태스크당 절반 비용으로 냈으며, Zapier AutomationBench 통과율은 차선 모델의 약 1.5배(동일 태스크당 비용)라고 밝혔다(Anthropic 공식 발표, 2026년 7월 24일). 인상적인 수치지만 자체 벤치마크이고, Anthropic 자신도 effort를 정할 때 벤치마크가 아니라 "당신의 평가 세트(evals)"를 기준으로 하라고 반복해서 안내한다. 우리 태스크에서의 스윕 없이는 어느 레벨이 맞는지 알 수 없다.

둘째, 비용은 항상 내려가지 않는다. Opus 5의 fast mode는 리서치 프리뷰이고 Claude API에서만 제공되며, 가격이 입력 100만 토큰당 10달러 / 출력 100만 토큰당 50달러다. 표준 가격의 두 배다. 그리고 Opus 4.7의 fast mode는 제거됐다. `claude-opus-4-7`에 `speed: "fast"`를 보내면 이제 에러가 반환되고, Opus 4.6과 달리 표준 속도로 폴백되지도 않는다(Claude Platform 릴리스 노트, 2026년 7월 24일). 예전 코드에 남아 있다면 조용히 실패하는 대신 깨지는 쪽이다.

셋째, 더 근본적인 문제는 모델 설정 바깥에 있다. 베슬AI 안재만 대표는 AI타임스 기고에서 기업 AI 에이전트가 PoC를 넘지 못하는 병목 셋을 꼽았다. 최적화되지 않은 도구 호출·API 처리로 응답이 수 분대로 늘어나는 문제(한 제조 기업은 3~5분 지연을 겪었고, 결국 직원들이 기존 검색 시스템을 선호하게 됐다), 범용 LLM이 산업 맥락을 담지 못하는 문제(한 금융 기업은 챗봇이 규정에 어긋난 대출 안내를 내놓아 컴플라이언스 위반에 직면했다), 그리고 운영 체계의 부재(한 유통 기업의 재고 에이전트는 계절 수요 변화를 반영하지 못해 6개월 안에 예측 정확도가 급락했다)다(AI타임스 기고, 2025년 10월 23일). effort 한 칸은 세 번째 문제의 일부만 건드린다. 모니터링과 재평가 체계가 없으면 잘 고른 설정도 몇 달 뒤 틀린 설정이 된다.

## 한 줄 정리

Opus 5로 옮길 때 먼저 할 일은 다이얼을 올리는 게 아니라, 이전 모델용 검증 지시문을 지우고 `xhigh`로 굳혀둔 설정을 기본값 `high`로 되돌린 뒤 우리 평가 세트에서 effort 스윕을 다시 돌리는 것이다. 그리고 캐시를 쓰는 세션 안에서는 그 값을 끝까지 건드리지 않는 것이다.
